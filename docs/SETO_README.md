# SETO — стенд сравнения вариантов размещения поликлиник

> Если ты только подключился к проекту — сначала [HANDOFF.md](HANDOFF.md).

Код эксперимента из пропозала v4: сравнить, какое качество размещения даёт
конвейер с VLM по сравнению с простыми геометодами, и даёт ли пользу именно
изображение.

Это **не продукт**, а стенд: он должен не «выбирать места», а честно мерить
и сравнивать. Отсюда все решения в коде — один расчёт метрик на все варианты,
одинаковые ограничения, фиксация протокола, запрет подмены одного варианта
другим.

## С чего начать

```bash
pip install -r requirements.txt     # Python 3.11+; pulp должен быть < 4
cp .env.example .env                # и вписать значения, см. ниже
python -m seto doctor moscow        # конфиги, git, данные, ключ, зависимости
python -m seto acquire moscow --snapshot-date 2026-10-08   # снимок OSM в raw/
#   растр населения — вручную, см. «Данные о населении»
python -m seto run-city moscow      # от снимка до отчёта, одной командой
python -m seto report <папка прогона>
pytest tests/                       # 219 проходят, 10 пропущены без снимка OSM
```

`run-city` на Москве занимает около 6 минут: 4 минуты общая подготовка,
остальное — варианты и метрики. Скоринг берётся из кэша, если он уже считался.
Каждый `run-city` заново делает подготовку города в новой папке прогона.

`snapshot_date` в `global.yaml` и дата папки в `raw/` обязаны совпадать:
`acquire` без `--snapshot-date` кладёт данные в папку с сегодняшней датой,
а `run-city` ищет их по `snapshot_date` из конфига.

## Данные о населении

`acquire` растр населения **не скачивает**. Его кладут вручную:

1. Скачать тайл GHS-POP E2025 R2023A, 100 м, Mollweide
   (`GHS_POP_E2025_GLOBE_R2023A_54009_100_V1_0_R3_C21.tif` для Москвы,
   24 МБ, лицензия CC BY 4.0) с сайта GHSL (Global Human Settlement Layer).
2. Положить в `raw/<город>/<snapshot_date>/` рядом с `osm.pbf`.
3. В папке должен быть ровно один `*.tif` — при двух `prepare-city` откажет.

Хеш растра в `data_manifest.json` не попадает (манифест пишет `acquire`
только по PBF). Для воспроизводимости запиши его вручную.

## Что нужно в `.env`

```
MODELS_BASE_URL=http://10.100.11.205/v1
MODELS_API_KEY=<ключ внутренних моделей>
SETO_DATA_ROOT=/path/to/seto-data  # вне синхронизируемой папки: там гигабайты
SETO_BIND_SOURCE_IP=<ip Wi-Fi>     # только если VPN забирает весь трафик
```

Последняя строка нужна, если на машине включён VPN «на весь трафик»: он
перехватывает маршрут до внутреннего сервера лаборатории. Правильное решение —
split-tunnel; это обход на случай, когда его нет.

## Сравниваемые варианты

| | что делает | что показывает |
|---|---|---|
| **A** | 1000 случайных допустимых наборов | нижняя планка |
| **B** | P-median, веса = население | вклад оптимизатора и данных о населении |
| **C** | та же VLM, вход — текст из OSM | оценщик тот же, информации меньше |
| **D** | та же VLM, вход — спутниковый снимок | проверяемая система |
| **M** | максимальное покрытие | верхняя граница по главной метрике |
| **E** | GIS-AHP | делает отдельная команда, мы принимаем решение; метрики по E код пока не считает |

Скор модели входит ровно одним способом — множителем веса спроса
`w = P·(1 + α·ŝ)`, где `ŝ` — min–max нормировка скора 0–10 по всем клеткам
города. При α = 1 вес клетки растёт не больше чем вдвое. Площадки скор не
фильтрует и не штрафует.
Поэтому разница **D − C** означает вклад именно изображения: оценщик,
промпт и всё остальное у них общее, различается только вход.

## Где что лежит

```
seto/
  acquire/   загрузка сырых данных, чтение PBF
  data/      граница, сетка, население, признаки, слои OSM
  routing/   пешеходный граф, привязка, матрица времён
  sites/     допустимые площадки и общие ограничения
  scoring/   промпты, вызов модели, веса спроса
  variants/  решатель A/B/M/C/D и приём внешнего E
  metrics/   покрытие, 2SFCA — один код на все варианты
  costs/     таймеры и журнал человеко-времени
  experiment/ оркестрация, протокол, чувствительность, пакет
  report/    таблицы и отчёт
  qa/        карты и инспектор для визуальной проверки
```

Данные и прогоны лежат вне репозитория, в `SETO_DATA_ROOT`:
`raw/<город>/<дата>/` только на чтение, `runs/<город>/<run_id>/` не
перезаписывается, `cache/vlm/<режим>/` — ответы модели, `human_log.csv` —
журнал `log-human`. Снимки для D ожидаются в
`raw/<город>/<дата>/imagery/<cell_id>.png`, по одному на клетку.

Что лежит в папке прогона `run-city`:

| файл | что |
|---|---|
| `report.md`, `report.json` | отчёт и сводка |
| `metrics_main.csv`, `metrics_thresholds.csv`, `differences.csv`, `metrics.parquet` | метрики |
| `solutions.json`, `random_A.parquet` | выбранные площадки и распределение A |
| `scores_text.parquet` | скор и обоснование (rationale) модели по каждой клетке |
| `grid.parquet`, `cell_features.parquet`, `clinics.csv`, `sites.parquet`, `times.npz` | подготовленные данные города |
| `clinics_uncertain.csv` | поликлиники с нетиповым названием — на ручную проверку |
| `costs.json`, `log.jsonl`, `manifest.json`, `effective_config.yaml` | затраты, журнал, воспроизводимость; сводка о данных города — поле `city` в `report.json` |

`sensitivity` дописывает в ту же папку `sensitivity_*.csv` и `sensitivity.json`.

## Чего стенд НЕ делает — и почему

- **не считает порог допустимой потери δ и ε.** Обоснованного основания нет,
  пилот описательный (п. 3.8 пропозала);
- **не выводит среднее `A_i` по 2SFCA.** При одинаковом k оно равно общей
  мощности делить на население и от размещения не зависит — метрика выглядела
  бы осмысленной и не мерила бы ничего;
- **не подменяет вариант D вариантом C,** когда снимков нет. Критерий качества
  определён через D, и отчёт честно пишет «нет данных»;
- **не чинит импортированное решение E.** Нарушение — отказ с причиной, иначе
  разница D − E мерила бы нашу правку, а не метод;
- **не ставит «выполнен» критериям пилота без D.** Все три критерия
  (качество, затраты, надёжность) определены через D;
- **не использует расстояния по прямой** нигде в решениях и метриках.
