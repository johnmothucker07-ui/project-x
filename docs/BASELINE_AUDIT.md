## ГЛАВНОЕ: стоп-условие п. 1 сработало

П. 1 предписывает остановиться, если скор входит в P-median не как множитель веса
спроса `w_i = P_i·(1 + α·ŝ_i)`. **Он так не входит, и P-median в MVP отсутствует.**

```python
# optimize/optimizer.py, solve()
problem += pulp.lpSum(cand["best_score"].iloc[i] * x[i] for i in range(n))  # цель
problem += pulp.lpSum(x) <= budget
problem += x[i] + x[j] <= 1   # для пар ближе min_dist
```

- Целевая функция — **сумма предрасчитанных скоров** выбранных клеток. Времени в ней нет.
- `time_matrix` приходит аргументом и не используется; из `scripts/04_optimize.py:20`
  туда передаётся буквально `None` с комментарием «пока не нужен».
- Формально это задача о взвешенном независимом наборе (knapsack с конфликтными парами),
  а не P-median и не MCLP, хотя модуль озаглавлен «P-Median / MCLP на PuLP».
- `wealth_score` от модели входит **только** в `profit_score`, то есть в частный сценарий.
  В государственном `equity_score = normalize(население) · normalize(1/(1+клиники))` —
  скора модели там нет ни в каком виде.

**Следствие:** в гос-сценарии у VLM в бейзлайне нет ни одного канала влияния на решение.
Связку `w_i = P_i·(1 + α·ŝ_i)` нужно реализовывать с нуля, бейзлайнная логика скоров
не переносится. Вынесено в `OPEN_DECISIONS.md` как Д4 (= Л4).

**Попутно:** формулировка «Исходное состояние» в списке работ — «выбор мест через
P-median с расстояниями по прямой» — неточна в первой половине. Расстояния по прямой
действительно, P-median нет. Стоит поправить, потому что на это описание опирается план.

## 4. Промпт и схема ответа

Файл `estimate/prompt.py`. Текст дословно:

```
Ты оцениваешь городской район по краткому описанию его окружения.
Дай КАЧЕСТВЕННЫЕ суждения — так, как если бы ты просто осмотрелся вокруг, без калькулятора.

ВАЖНО: ничего не вычисляй. Не оценивай население, спрос, расстояния или количество объектов —
эти числа приходят из данных, а не от тебя. Оцени только «на глаз».

Описание окружения района:
"{context_text}"

Верни СТРОГО один JSON-объект, без markdown и без пояснений, ровно с такими полями:
{
  "wealth_score": целое число 0-10 — насколько богато/премиально выглядит район,
  "area_character": одно из "residential", "commercial", "industrial", "mixed" — тип района,
  "confidence": число от 0 до 1 — насколько ты уверен в оценке
}
```

Схема ответа MVP: `wealth_score` (int 0–10), `area_character` (enum из четырёх),
`confidence` (float 0–1). Парсер `parse_response` снимает markdown-обёртку, выдёргивает
первый JSON-объект регуляркой, проверяет наличие полей, диапазоны и допустимые категории.

**Расхождение со списком.** П. 7.1 требует схему `{"score": <число>, "rationale": "<строка>"}`
и промпт, спрашивающий **одно**: насколько клетка нуждается в первичной медицинской
помощи. Промпт MVP спрашивает другое — премиальность района и тип застройки. Это не
«тот же промпт с заменённой фразой про изображение», а другой вопрос.

Значит «промпт D дословно из MVP» (п. 1, п. 7.1) выполнить нельзя: придётся писать новый
под нужный вопрос. Это стоит зафиксировать отдельным решением — наследуется не промпт,
а только формат строгого JSON и парсер.

**Что переиспользуем:** `parse_response` как основу — чистка markdown и извлечение
первого объекта пригодятся. Добавить: защиту от `content: null` (нужна при переходе
на Qwen-reasoning, см. Д1) и валидацию через pydantic вместо ручных проверок.

## 6. OSM: что и откуда парсится

**Источник — живой Overpass**, `https://overpass-api.de/api/interpreter`, запрос POST
form-полем `data=` (иначе 406), User-Agent обязателен. Снимка PBF нет.
П. 4.3 живые запросы при расчётах запрещает — слой переписывается целиком.

### 6.1. Медучреждения — `data/osm.py:fetch_pois`

- теги: `amenity=clinic|hospital|doctors`, `healthcare=clinic`;
- сохраняемые поля: `osm_id, osm_type, name, amenity, healthcare, lon, lat`;
- **`operator` и `operator:type` не сохраняются** → гос и частные в пайплайне
  неразличимы в принципе;
- `healthcare:speciality` не сохраняется → профиля нет;
- фильтры: `exclude_healthcare: [laboratory, rehabilitation, psychotherapist, dentist]`
  и стоп-слова по названию (`космет`, `стоматолог`, `дентал`, `beauty`, …).

Фактический результат прогона: 439 объектов — `amenity`: clinic 361, doctors 65,
hospital 12, `clinic;doctors` 1. По `healthcare`: clinic 300, doctor 58, hospital 10,
**NaN 71**. Без имени 8.

**Что заменяем.** Полностью: п. 4.5 требует кандидатов из OSM + реестр + геокодирование
+ сопоставление + ручную проверку + классификацию «государственная, взрослая, первичная».
Набор MVP из 439 разнородных объектов базовой сетью пропозала не является.

Ориентир масштаба: подсеть со словом «поликлиник» в названии — 40 объектов из 439.

### 6.2. Конкуренты — `count_competitors`

`gpd.sjoin(..., predicate="within")` — клиники считаются **строго внутри клетки**,
без радиуса. Клиника в 50 м за границей не существует для этой клетки.

Фактически: 47 клеток из 182 в плотной Москве получили «медучреждений рядом не обнаружено».

### 6.3. Контекст для модели — `build_context_text`

Вариант A: только медучреждения, только внутри клетки. Шаблон
`"Рядом медучреждений: N (клиники: n, ...)."`

Фактически: **40 уникальных строк на 182 клетки**. Контекст беден настолько, что
`area_character` вышел `residential` во всех 182 клетках, а `wealth_score` принял
**4 различных значения** (3, 5, 6, 7; значение 6 — у 65 клеток) и коррелирует с числом
клиник на **ρ = 0,929**. То есть в бейзлайне `wealth_score` — это счётчик клиник.

**Что заменяем.** П. 7.3: текст варианта C строится из `cell_features` по фиксированному
шаблону. Код `build_context_text` не переиспользуется.

### 6.4. Окружение — `fetch_environment`, `environment_features`

Написано в коммите `b636ae0`, качества приличного: фиксированный словарь тегов из config
(42 категории), тайлинг bbox (на весь район Overpass отвечает 504), ретраи с
экспоненциальным backoff, дисковый кэш по тайлам.

**Но в пайплайн не подключено:** ни один скрипт не вызывает эти функции.
`data/interim/env_features.parquet` (182 × 44) создан ad hoc и не воспроизводится.

`landuse` тянется, но сознательно исключён из признаков (`_EXCLUDED_FROM_FEATURES`):
Overpass отдаёт полигон центроидом (`out center`), и крупный полигон засчитался бы
в одну клетку.

**Что переиспользуем.** Идею фиксированного словаря (без неё города несравнимы),
тайлинг и кэш — как образец устойчивости к Overpass. Сам код — нет: п. 4.3 требует
чтения из снимка PBF и **настоящих полигонов**, которые как раз нужны для допустимых
площадок (вода, промзоны, парки, ж/д).

## 8. Скоры

Файл `optimize/scores.py`.

```python
_scarcity(cells) = normalize(1 / (1 + cells["existing_clinics"]))
equity_score(cells) = normalize(normalize(население) * _scarcity(cells))
profit_score(cells) = normalize(normalize(население) * normalize(wealth_score) * _scarcity(cells))
```

- `normalize` — min-max **внутри района**. Между городами такие скоры несравнимы;
  для KPI переносимости это важно.
- `_scarcity` в докстринге назван прокси компоненты «далеко до ближайшей» — расстояние
  в скоры не входит вообще, только счётчик клиник внутри клетки.

**Что заменяем.** Всё. По пропозалу веса спроса — `w_i = P_i·(1 + α·ŝ_i)`, нормализация
`ŝ` по всем клеткам города (п. 7.1), и никаких составных индексов.

## 9. Маршрутизация

Файл `optimize/routing.py`. `travel_time_matrix(sources, destinations, osrm_url=None)`
принимает `osrm_url` и **игнорирует его**: внутри haversine и константа
`_AVG_SPEED_KMH = 25.0`. `nearest_clinic_time` — минимум по строке матрицы.

Сложность — наивная O(|S|·|D|) двойным циклом на Python.

**Что заменяем.** Всё: п. 6 требует пешеходный граф из снимка OSM, привязку через
KD-дерево с `snap_max_m`, время подхода, Дейкстру с отсечкой `t_max`, разреженное
хранение. Сигнатуры с `osrm_url` не переносятся — OSRM в плане нет, граф строится локально.

| принцип «все параметры в config, ничего в коде» | сетка (градусы → UTM, границы города) |
| площадно-взвешенный перенос населения (принцип) | источник населения (Д9) |
| дисковый кэш ответов модели (механизм) | ключ кэша (должен включать вход) |
| `parse_response` как основа парсера | промпт и схема ответа (другой вопрос к модели) |
| провайдер-независимость вызова модели | эндпоинт и модель (Д1, Д2) |
| фиксированный словарь тегов OSM (принцип) | источник OSM (Overpass → снимок PBF), полигоны вместо центроидов |
| тонкие скрипты + логика в пакете | структура выходов (`raw/`, `runs/`, манифест) |
| `baseline_placement` как идея варианта A | скоры, маршрутизация, оптимизатор, метрики — всё |

Переиспользуемого мало, и это ожидаемо: пропозал меняет и постановку задачи,
и требования к воспроизводимости. Ценность бейзлайна — в отлаженных мелочах
(обход 406 у Overpass, тайлинг, backoff, кэш) и в понимании, где он ошибается.
